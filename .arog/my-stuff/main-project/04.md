# Module 4: The Permanent Record — Aurora DSQL

## Teaching Arc

- **Metaphor:** A court reporter's transcript. Every single proceeding gets typed into the permanent record, word for word, and nothing is ever torn out or overwritten. If a witness needs to correct an earlier statement, the correction is entered as a brand-new statement — "let the record show the previous statement is superseded" — while the original stays exactly as it was, timestamped, forever.
- **Opening hook:** Module 3 showed how every domain constantly ASKS questions through GraphQL. This module covers the one place any event is allowed to CHANGE anything: `commit()` — the last step of the fixed lifecycle — writing directly into **Aurora DSQL**, a distributed, Postgres-compatible database.
- **Key insight:** Nothing in this database is ever truly overwritten or deleted. Every table carries a pair of "when was this true" timestamps (a pattern called **bi-temporal**). "Updating" a record almost always means: close the old row's validity window and insert a brand-new row — never a plain `UPDATE ... SET`. This is true across domains, not just one.
- **"Why should I care?":** This is one of the most important patterns in serious business software: a full, provable audit trail. If you're asked to add a "history" or "who changed what and when" feature to anything, this is the exact pattern to reach for — and now you know its name and its shape.

```typescript
// Step 1: Close previous version
const closeResult = await dataDb.update<OrganizationPolicyTable>({
  table: "data.OrganizationPolicy",
  fields: {
    _ValidityEndDateTime: closedAt,
    _TransactionStartDateTime: closedAt,
  },
  where: `OrganizationPolicyID = ${escape(input.organizationPolicyID)} AND ClientID = ${escape(clientID)} AND (_ValidityEndDateTime IS NULL OR _ValidityEndDateTime >= '9999-12-31')`,
});

if (closeResult.affectedRows !== 1) {
  throw new Error(
    `organizationPolicy.update: Close UPDATE expected 1 row, got ${closeResult.affectedRows}. Race condition — previous version already closed.`,
  );
}

// Step 2: Insert new version row
const insertResult = await dataDb.insert<OrganizationPolicyTable>({
  table: "data.OrganizationPolicy",
  row: {
    OrganizationPolicyID: newOrganizationPolicyID,
    ParentOrganizationPolicyID: input.organizationPolicyID,
    PolicyName: input.policyName,
    VersionNumber: newVersionNumber,
    EventID: this.eventID,
    _ValidityStartDateTime: closedAt, // contiguous — same as closed row's _ValidityEndDateTime
    _ValidityEndDateTime: new Date("9999-12-31T00:00:00.000Z"),
  } as any,
});
```

## The 4 bi-temporal columns, on every table in this database (for a table or icon-rows)

| Column                      | Meaning                                                              |
| --------------------------- | -------------------------------------------------------------------- |
| `_ValidityStartDateTime`    | When this row started being true in the real world                   |
| `_ValidityEndDateTime`      | When this row stopped being true (`9999-12-31` = "still true today") |
| `_TransactionStartDateTime` | When the database recorded this row                                  |
| `_TransactionEndDateTime`   | When the database recorded that it stopped being current             |

**How to tell "is this row still active" in any query on this platform:** `WHERE _ValidityEndDateTime IS NULL OR _ValidityEndDateTime >= '9999-12-31'` — this exact shape appears throughout the codebase, in every domain that writes to Aurora DSQL.

## Verified, real platform-wide security rule (great callout material)

> Every single insert always sets `ClientID` from `this.clientID` / the session — **never from user input**. This appears verbatim in both the `create` and `update` snippets above, and it's a documented, non-negotiable platform rule: the three fields `ClientID`, `EventID`, and `VersionNumber` (on create) must always come from trusted, session-derived values, never from anything a user typed or a request body sent — a real security boundary, not a style preference.

- [x] **Data flow / message flow animation** — **this module owns the course's second mandatory flow animation.** Actors: **Event** (actor-3), **Aurora DSQL** (actor-4). Steps (model on the update.tsx sequence):
  1. highlight Event — "commit() begins. Everything from here happens in one transaction."
  2. packet Event → DSQL, label: "Step 1: CLOSE the old row — set its end-of-validity timestamp to right now."
  3. highlight DSQL — "Exactly 1 row closed. If this affected 0 or 2+ rows, commit() throws immediately — something's already wrong."
  4. packet Event → DSQL, label: "Step 2: INSERT a brand-new row — new ID, version number bumped by 1, linked back to the row it replaces."
  5. highlight Event — "Both writes succeeded — the transaction commits for real. Any failure at any step rolls back everything, cleanly."
- [x] **Quiz** — 3-4 questions, style: tracing + security.
  - Q1 (tracing): "A record is 'updated.' Does its unique ID stay the same, or change?" (It changes — a brand-new row with a new ID is inserted; the old row is closed, not edited.)
  - Q2 (security): "Where should `ClientID` come from when writing a new row — the request body, or the session?" (Always the session — never trust a client-supplied value for a security-sensitive field like this.)
  - Q3 (application): "You need to answer 'what did this record look like last month?' Which columns do you filter on?" (The `_ValidityStartDateTime` / `_ValidityEndDateTime` bi-temporal window — not just 'the latest row.')
