# Module 2: Meet the Actors — Conversations, Events & Friends

## Teaching Arc

- **Metaphor:** An orchestra. The concertmaster (the **conversation**) faces the audience, takes requests, and sets the mood — but never actually plays the piece. The section players (the **events**) are the ones who actually perform, and they follow a strict, fixed score from start to finish, in the exact same order, every single time — no improvising the order. Ushers (**GraphQL**) fetch programme information the moment anyone asks. And there's a sound engineer in the booth (**CloudWatch**) recording literally everything, the whole concert, for later review.
- **Opening hook:** Every one of the hundreds of canonicals across all 14 domains is really built from the same small cast of characters, wearing different costumes. Once you can name the 4-6 "roles" in this orchestra, you can read ANY domain's code — not just the one you already know.
- **Key insight:** Each domain exposes the same standard set of pieces: **controllers** (conversations — chat UI, never touch the database), **events** (business logic — the only place that writes data, in a fixed lifecycle order), **api** (routes canonicals to the right controller), and **triggers** (background/async work). Plus two more specialized pieces: **experiences** (metadata-driven workflow screens) and **grids** (data tables). Confirmed identical in both `hr/` and `accounting/` — this isn't a coincidence, it's the platform's shape.
- **"Why should I care?":** When an AI suggests "let's add this logic to the controller," you'll immediately know to ask "wait, does this need to survive a page refresh / get written to the database? Then it belongs in the event, not the controller." Knowing the cast of characters is what lets you correct an AI's file-placement mistakes.

## The cast of characters (for pattern-cards or icon-rows)

| Role                          | Folder         | Job                                                                      | Never does                               |
| ----------------------------- | -------------- | ------------------------------------------------------------------------ | ---------------------------------------- |
| **Conversation** (controller) | `controllers/` | Talks to the person — asks questions, shows dropdowns, collects input    | Never writes to the database directly    |
| **Event**                     | `events/`      | All validation + all database writes, in the fixed lifecycle order above | Never renders a chat message             |
| **API**                       | `api/`         | Routes an incoming canonical + request type to the right controller      | Never contains business logic itself     |
| **Triggers**                  | `triggers/`    | Background/async work not tied to a live conversation                    | Not part of a person's live chat session |
| **Experiences**               | `experiences/` | Metadata-driven workflow screens (form-based, not chat-based)            | Optional — not every domain needs these  |
| **Grids**                     | `grids/`       | Data-table read views (e.g. a list of policies, a list of pay runs)      | Read-only, not where writes happen       |

## A concrete, verified rule from this platform's own written conventions

> **UUIDs (unique IDs) are only ever generated inside `setOutput()`** — never inside `validateInput()` or `commit()`, because those two methods can each run more than once per request (retries, per-field validation loops), and generating an ID twice would create two different IDs for what should be the same record. `setOutput()` runs exactly once. This is a real, documented platform rule, not a guess — worth remembering the next time you (or an AI) need to add a new ID field to an event.

Explain generics (`Input`, `Output`, `WorkArea`) as "three related shapes: what comes in, what goes out, and scratch space in between — every event declares its own version of these three."

Suggested message sequence (rewrite naturally, don't paste verbatim):
  1. Conversation: "I just collected everything I need from the user — handing off now."
  2. Event: "Got it. Starting with `initialize()` — let me check a few facts before touching anything."
  3. Event → GraphQL: "Quick question — is this legal entity/pay period/associate actually real?"
  4. GraphQL: "Confirmed — here's what you asked for."
  5. Event: "Validation passed. Running `setOutput()` now — this is the only place I generate new IDs."
  6. Event → Aurora DSQL: "Write this, please — this is the one and only place I'm allowed to."
  7. Aurora DSQL: "Done. Row written."
  8. Event → CloudWatch: "Logging every step of that, in case anyone needs to check later."
- [x] **Quiz** — 3-4 questions, style: architecture decision.
  - Q1: "An AI suggests writing a value directly to the database from inside a `.ctrl.tsx` file. Consistent with this platform's pattern?" (No — controllers never write to the database; only events do, and only inside `commit()`.)
  - Q2: "Where would you generate a brand-new ID for a record — `validateInput()`, `setOutput()`, or `commit()`?" (`setOutput()` — the only lifecycle method guaranteed to run exactly once.)
  - Q3 (tracing): "You're dropped into a domain you've never seen before and told 'find the actual business logic.' Which folder do you open first?" (`events/` — controllers only handle the conversation, not the logic.)
