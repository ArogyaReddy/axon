# Module 3: Asking Questions — GraphQL Across the Platform

## Teaching Arc

- **Metaphor:** Air traffic control radio calls. A pilot (any piece of code, anywhere in the platform) keys the radio and asks the tower a very precise question — "requesting altitude clearance" — and gets back exactly that, nothing more. The tower never flies the plane, never changes course, never touches the controls — it only answers what it's asked. And if the radio briefly cuts out, a well-trained pilot doesn't crash — they note it, try again or proceed with what they already know, and keep flying.
- **Opening hook:** Every single one of the 14 domains, in every event and every conversation, asks questions the exact same way: **GraphQL**. It's the platform's one universal "radio channel" for reading data — never for changing it.
- **Key insight:** GraphQL in this codebase is used through one consistent call shape — `this.session.api.query({ query: \`...\`, variables: {...} })` — always a read, never a write. Many of these reads are deliberately **fail-open**: if the question can't be answered, the code logs it and quietly continues with a safe default rather than stopping everything.
- **"Why should I care?":** "Why is this dropdown empty" or "why did this field come back blank" almost always traces back to a GraphQL read — and knowing the fail-open pattern tells you why the whole request didn't just crash. It's also a precise, reusable instruction you can give an AI: "make this read fail-open, matching the existing pattern in this codebase," instead of vaguely saying "handle errors."

**File: `src/hr/events/organizationPolicy.create/organizationPolicy.create.tsx` (a complete, real, fail-open GraphQL read — ~lines 979-1023)**

```typescript
	private async fetchLegalEntity(legalEntityID: string): Promise<{
		legalEntityID: string;
		legalEntityName: string;
		clientID: string;
	} | null> {
		try {
			const result = await this.session.api.query({
				query: `
					query organizationPolicyCreate_validateLegalEntity($legalEntityID: ID!) {
						legalEntity(legalEntityID: $legalEntityID) {
							legalEntityID
							legalEntityName
							client {
								clientID
							}
						}
					}
				`,
				variables: { legalEntityID },
			} as Query);

			const le = result.data?.legalEntity;
			if (!le || !le.legalEntityID || !le.legalEntityName || !le.client?.clientID) {
				this.log.warn({
					message: 'organizationPolicy.create: fetchLegalEntity incomplete GraphQL response',
					data: { legalEntityID, response: le }
				});
				return null;
			}
			return {
				legalEntityID: le.legalEntityID,
				legalEntityName: le.legalEntityName,
				clientID: le.client.clientID,
			};
		} catch (err) {
			this.log.error({
				message: 'organizationPolicy.create: fetchLegalEntity error',
				data: {
					legalEntityID,
					error: err instanceof Error ? err.message : String(err),
					stack: err instanceof Error ? err.stack : undefined,
					errorObject: err
				}
			});
			return null;
		}
	}
```

## The pattern, stated plainly (for a callout-accent box)

Every GraphQL call in this codebase — no matter which of the 14 domains, no matter whether it's a controller or an event — follows the same shape: `session.api.query({ query: <a GraphQL query string>, variables: {...} })`, and it always returns data, never changes it. Writes happen through a completely different path (Module 4). If you ever see `session.api.query(...)` in this codebase, you already know: it's a read, and you already know roughly what it looks like.
