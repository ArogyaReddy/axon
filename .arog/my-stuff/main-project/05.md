# Module 5: Mission Control — AWS & CloudWatch

## Teaching Arc

- **Metaphor:** Mission control at a space agency. Dozens of independent systems (14 domains' worth of Lambda functions) are all running at once, each doing its own specialized job — but every single one reports its telemetry back to one mission control room that's watching continuously. Different consoles in that room handle different jobs: one tracks the archive of everything ever recorded (S3), one holds a fast lookup board of current configuration (DynamoDB), one is the intercom system for passing messages between teams (SQS/SNS), one checks badges at the door (Cognito) — and one wall of screens, CloudWatch, shows the live and historical feed from everything, all at once.
- **Opening hook:** This platform doesn't run on one server somewhere — it runs as many small, independent pieces of code (Lambda functions) hosted on Amazon Web Services (AWS), and it leans on a specific, real, verifiable set of AWS services to do it.
- **Key insight:** The verified AWS services this codebase actually depends on (confirmed directly in `package.json`, not guessed) include: **Lambda** (where the code runs), **S3** (file storage — Lambda deployment packages and assets), **DynamoDB** (a separate database used only for platform metadata — never for real business data), **CloudWatch + CloudWatch Logs** (observability — where every `this.log.*` call ends up automatically), **Cognito** (authentication), **SES v2** (email), and several more specialized services (Connect, Location, QuickSight, Pinpoint, EC2, ECS).
- **"Why should I care?":** Knowing exactly which AWS services are really in play (not a guess, not "the cloud") means you can reason about cost, rate limits, and failure modes — and you'll immediately recognize CloudWatch as the single source of truth for "what actually happened" whenever something breaks.

## The 3-store rule — a common source of confusion, worth its own callout

There are **three separate stores** in this platform, and confusing them is one of the most common mistakes:

| Store                             | Holds                                                                                | Written by                                                                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Aurora DSQL** (`data.*` tables) | The actual committed business data — policies, pay runs, whatever the domain manages | `commit()`, and only `commit()`                                                                                                                                 |
| **DynamoDB (via `meta/`)**        | Platform _metadata_ only — field vocabulary, UI labels, grid wiring, NLU phrases     | A completely separate build (`meta/` has its own `package.json`, its own `Makefile`, its own deploy step) — never touched by the event code you write in `src/` |
| **CloudWatch Logs**               | Every `this.log.*` call, automatically, from every Lambda                            | Nothing to "deploy" — it's just where logs already go                                                                                                           |

`meta/` being a genuinely separate package (verified: its own `package.json`, `Makefile`, `Dockerfile`, own `tsconfig.json`) is not an accident — it's built and deployed on a completely different pipeline than the rest of the code, which is exactly why a stale `meta/build/` causes a silent failure with no compile-time warning: `src/` never reads `meta/` at runtime, only the already-deployed DynamoDB data.
