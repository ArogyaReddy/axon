# Module 1: Welcome to adp-e-product

## Teaching Arc

- **Metaphor:** A big shopping mall with many independent stores. Each store (a business domain — payroll, HR, benefits, accounting...) runs its own operation and sells its own thing, but every single store shares the same mall-wide infrastructure: the same electrical grid, the same security system, the same directory board at the entrance. In this codebase, that shared infrastructure is a folder literally called `shared/`, and the "directory board" is a separate system called `meta/`.
- **Opening hook:** Imagine an HR admin clicks one button to create a company policy, or a payroll administrator clicks one button to submit payroll. Both clicks kick off the exact same kind of machinery underneath — even though they're completely different business domains, built by different teams, for different purposes. This course is about that shared machinery.
- **Key insight:** `adp-e-product` is not one app — it's 14 independent business domains (payroll, HR, benefits, accounting, and more) that all follow the same architectural rules, because they all import from one shared foundation and are held together by one shared event-and-conversation pattern.
- **"Why should I care?":** Once you understand the shape of ONE domain, you understand the shape of all 14 — including whichever one you get assigned to work in. This module gives you the map before you walk in the door.

## What this app actually does (ground the course in reality, plain English)

`adp-e-product` powers ADP's employee-experience platform — the software behind everyday workplace actions like: an HR admin creating a company policy and assigning it to staff, a payroll administrator submitting a pay run, an employee checking their pay statement, a manager approving a request. Every one of those actions is called a **canonical** (a fixed `noun.verb` name, like `payroll.submit` or `organizationPolicy.create`) and every canonical is handled by the exact same underlying pattern, covered module by module in this course.

## One concrete worked example to trace (use as a "step-cards" or "flow-steps" hook)

Someone clicks "Submit Payroll" in the product. Behind the scenes: (1) a **conversation** (chat-style UI code) asks a few clarifying questions, (2) on submit, an **event** (business-logic code) runs a strict, fixed sequence of validation and write steps, (3) along the way it asks other systems questions via **GraphQL**, (4) it permanently records what happened in **Aurora DSQL** (the database), and (5) every step is silently recorded to **CloudWatch** so it can be traced later. This exact 5-step shape repeats for organizationPolicy.create, for worker.hire, for literally any of the hundreds of canonicals across all 14 domains — it's the one shape you need to learn once.
