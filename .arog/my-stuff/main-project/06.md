# Module 6: Pre-Flight Checklist — From Zero to Shipped

## Teaching Arc

- **Metaphor:** A pilot's pre-flight checklist. Before a plane is cleared for takeoff, there's a strict, ordered sequence of checks — and skipping one (like "did anyone actually verify the fuel gauge, or just glance at it") doesn't always fail loudly; sometimes the plane takes off fine and the problem only shows up later, mid-flight. This platform has its own real pre-flight checklist for getting code from your laptop into a real environment — and several of its steps fail _silently_ if skipped, exactly like a skipped instrument check.
- **Opening hook:** Everything in Modules 1-5 explained how the code works. This module is different — it's the actual, verified sequence of commands you'd run to go from "just cloned this repo" to "my change is live," plus the specific mistakes that cause real, documented incidents.
- **Key insight:** This platform is built with `make` + `npm`, has a genuinely separate metadata build (`meta/`) that must be rebuilt and redeployed independently, and ships through Jenkins based on your branch name — and several of the platform's own written rules exist specifically because skipping a step failed silently in production before.
- **"Why should I care?":** This is the module that actually gets you "up and ready for project coding" — the rest of the course explains the machine, this module hands you the keys and the ignition sequence.

**Real, verified commands from `Makefile` (root) — the mandatory build order**

```
make root                   # step 1 — always first
make shared                 # step 2 — always second, before any domain
make -j 6 all                # builds all 14 domains in parallel (does NOT rebuild root/shared)
make -j 6 <domain-name>      # e.g. make -j 6 payroll — build just one domain
make -j 6 meta                # the separate metadata build
make -j 6 i18n                # the translation-string build
make -j 6 clean                # clean build artifacts
```

## The mandatory rules that exist because of a real incident (verbatim from this platform's own written conventions — do not soften or generalize these)

1. **Never add an import in `src/shared/` without confirming the package is listed in the ROOT `package.json`** (not just one domain's `package.json`). A package only in a domain's `devDependencies` breaks every domain that depends on `shared/`, not just the one you're working in.
2. **Never push a change touching `meta/src/` without rebuilding `meta/build/` first** (`make meta`, then `npm run load-meta -- FIT`). A stale `meta/build/` causes a silent authentication-style error in a real environment, with zero compile-time warning.
3. **Never leave a translation call without a matching key in the domain's i18n JSON file.** A missing key does not throw an error — it silently renders the raw key text directly in production UI (e.g. showing `PROMPT/DUE_TIME` on screen instead of real text).
4. **The event lifecycle always runs in exactly this order, never reordered or partially skipped:** `initialize() → validateInput() ×n → validateEvent() → setWorkArea() → setOutput() → setTitle() → setSummary() → preCommit() → commit()`.
5. **Three fields must never come from user input:** `ClientID` (always from the session), `EventID` (always `this.eventID`), `VersionNumber` (hardcoded `1` on create) — a real security boundary, not a style choice.
6. **Generate new IDs only inside `setOutput()`** — never in `validateInput()` or `commit()`, since those can each run more than once per request.
7. **Every table insert sets 4 bi-temporal timestamp fields** (covered in Module 4) — this is enforced everywhere, not optional.
8. **Never ask a teammate (or an AI's user) to "test it yourself, reload the browser."** Verify with real tools — run the actual test, check the actual log, read the actual file — before calling anything done.

## Interactive Elements

- [x] **Code↔English translation** — use the Makefile command block. Explain why `make root` and `make shared` must run separately and first ("everything else depends on them"), and why `make -j 6 all` explicitly does NOT redo those two steps (efficiency — you only rebuild the foundation when the foundation actually changed).
- [x] **Data flow / message flow animation** — model the real "zero to shipped" sequence as a flow. Actors: **You** (actor-1), **Local Build** (actor-3), **Meta Build** (actor-4), **Jenkins** (actor-5). Steps:
  1. highlight You — "Clone the repo, run `npm install` at the root."
  2. packet You → Local Build, label: "Run make root, then make shared — always in that order, always first."
  3. packet Local Build → Local Build, label: "Run make -j 6 <your-domain> to build just the domain you're working in."
  4. highlight Local Build — "Compile, lint, and run check-controllers / check-event-types before you trust anything."
  5. packet You → Meta Build, label: "Touched meta/src/? Rebuild it separately: make meta, then load it — this step is easy to forget and fails silently if skipped."
  6. packet You → Jenkins, label: "Push your branch. Jenkins reads the branch name itself to decide which environment gets your change."
- [x] **Quiz** — 3-4 questions, style: application + "spot the mistake."
  - Q1: "You changed a file inside `meta/src/`. You compile your domain and it succeeds with no errors. Are you safe to consider this done?" (No — `meta/` is a separate build; a successful domain compile says nothing about whether `meta/build/` is stale. You still need to rebuild and redeploy meta separately.)
  - Q2 (application): "You add a brand-new npm package that only `shared/` code needs. Where must it be listed?" (The ROOT `package.json` — not just the domain you happened to be working in, or it silently breaks every other domain that imports `shared/`.)
  - Q3 (spot the mistake): "An AI tells you 'looks correct, you're good to ship' right after editing a file, without running anything. What's missing?" (Actual verification — running the real command, checking the real output — 'looks correct' is not the same as verified.)
